# How the golden set was built

**Read this before believing any number in the report.**

## The one-paragraph version

220 examples were drawn from the **held-out test split** (the newest 15% of threads by
timestamp), **stratified** by a cheap machine intent pass with a floor of 12 per intent
and a deliberate 15% hard-case quota. Each example was then labelled **twice by machine**
— Pass A and Pass B use different models, different prompt framings, different intent
orderings and a different item order — and their agreement is reported below as a
reliability estimate. Every example the two passes disagreed on, plus a random 20% audit
of the ones they agreed on, goes to a **human review queue**. Only examples a human has
actually opened are marked `human_adjudicated`.

**These are machine labels with a human adjudication pass over the contested subset.**
They are not 220 hand-written labels, and nothing in this repository describes them as
such. Any example a human has not seen carries `provisional: true`, and `run_eval.py`
stamps **PROVISIONAL** on every headline number while any provisional rows remain.

## Why the test split only

The retrieval corpus is the oldest 70% of threads. The golden set comes from the newest
15%. Nothing the agent can retrieve is ever something it is graded on, and
`retrieval.assert_no_leakage()` fails loudly on every decision if a retrieved id turns up
in dev or test. A random split would have put near-duplicate future threads into the
index and inflated reply quality invisibly.

## Why stratified, and what that costs

Allocation is proportional to the observed intent distribution **with a floor of 12**, so
per-class F1 is not computed on two examples. The floor was met for all 11 intents.

> **The golden set is therefore NOT a random sample of production traffic.**
> `feature_request_or_complaint` is 38% of the real test split but 22% of the golden set;
> rare intents are over-represented by design. Two direct consequences, both repeated in
> the report:
> 1. **Macro-F1 over this set flatters rare classes** relative to what a
>    volume-weighted production metric would show.
> 2. **The deflection rate measured here does not transfer to real inbound volume.**
>    A production estimate would need re-weighting to the true intent mix.

## The hard-case quota

15% of the sample is deliberately hard: sarcasm, multi-intent, very short messages, and
messages carrying escalation triggers. Support systems fail precisely on these, and a
golden set of easy cases would measure nothing worth knowing.

Note on the definition: plain negation is **not** treated as a hard case on its own.
Nearly every support complaint contains one ("my music *won't* play"), and counting it
alone flagged 24% of the sample as hard, which made the quota meaningless. Negation
counts only in combination with another signal.

## Exact reproduction

```bash
python scripts/prelabel.py --stage stratify   # intent pass over the whole test split
python scripts/sample_golden.py               # -> golden/sample_220.jsonl
python scripts/prelabel.py --stage A          # -> golden/prelabel_A.jsonl
python scripts/prelabel.py --stage B          # -> golden/prelabel_B.jsonl
python scripts/ab_agreement.py                # -> kappa + golden/review_queue.jsonl
python golden/label_cli.py                    # THE HUMAN PASS
python scripts/build_golden.py                # -> golden/v1.jsonl
python scripts/validate_golden.py             # schema gate
```

`random_state = 20260909` everywhere. Sampling metadata, including the exact per-intent
allocation and the pool it was drawn from, is in `golden/sampling_meta.json`.

## What "escalate" means here

**The escalation policy is my invention.** Spotify's real routing rules are unobservable
from this dataset — we only see what they posted publicly, never what their internal
tooling decided. So router "accuracy" measures **agreement with a policy I wrote**, not
correctness. The policy is stated in full in `src/support_agent/config.py`
(`ESCALATION_REASON_CODES`) and in the Pass A prompt in `scripts/prelabel.py`.

## Why `reply_must_include` / `reply_must_not_include` instead of reference replies

There is no single correct reply to an open-ended support message, so grading against one
"gold" reply would mostly measure paraphrase distance. Instead each example carries 2–3
things any acceptable reply **must do** ("acknowledge the double charge", "point to the
refund process") and 1–3 things it **must not do** ("promise a specific refund amount",
"ask for card details"). These are checked mechanically, cost nothing, and are far more
defensible than an LLM similarity score against one arbitrary reference.

## Known limitations of this golden set

1. **One annotator.** The human pass is a single non-expert (me), not Spotify's support
   organisation. My labels are the ceiling on measured accuracy: a system that disagrees
   with me is scored wrong even where it might be right.
2. **No second human**, so there is no human–human kappa — only machine–machine kappa and
   a single human's adjudication over the contested subset. A real inter-annotator
   agreement figure is the single highest-value thing another week would buy.
3. **Survivorship bias upstream.** The pool is only threads that survived the
   resolution-bearing filter, i.e. problems SpotifyCares chose to answer publicly and
   substantively. Anything moved to DM — which is most billing and account work — is
   invisible.
4. **Machine pre-labels anchor the human.** Showing Pass A and Pass B during adjudication
   makes review fast but risks the human rubber-stamping. The random 20% audit of
   agreements exists to make that failure detectable rather than silent.
